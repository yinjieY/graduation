# 农产品溯源系统 — 项目交接文档

## 一、项目背景

### 1.1 问题描述

农产品质量安全是食品安全的重要环节。传统农产品溯源系统存在以下问题：

- **数据可篡改**：溯源信息存储在中心化数据库中，内部人员可修改或删除数据，消费者无法验证信息真实性
- **二维码可伪造**：缺乏密码学保护，造假者可复制或编造溯源二维码
- **异常扫码难检测**：缺乏智能风险评估，无法识别批量造假、跨区域复扫等异常行为
- **消费者反馈无保障**：投诉记录可被删除，消费者维权困难

### 1.2 解决方案

本项目构建了一个基于 **区块链 + AI + 国密签名** 的农产品溯源系统，核心解决思路：

| 问题 | 解决方案 | 技术 |
|------|---------|------|
| 数据可篡改 | 关键操作上链存证，不可篡改可验证 | FISCO BCOS 联盟链 |
| 二维码可伪造 | 二维码签发时 SM2 签名，扫码时验签 | 国密 SM2 签名算法 |
| 异常扫码难检测 | 规则引擎 + AI 融合风险评估 | Drools + ONNX 知识蒸馏模型 |
| 消费者反馈无保障 | 反馈记录上链存证 | 区块链存证 |

## 三、功能模块详解

### 3.1 溯源二维码管理模块 (qs-trace-service)

**核心功能**：

| 功能 | 说明 | API |
|------|------|-----|
| 企业管理 | 企业注册审核、信息维护 | `/trace/company/**` |
| 产品批次管理 | 创建批次、关联企业 | `/trace/batch/**` |
| 二维码生成 | 生成含SM2签名的溯源二维码 | `/trace/qs/generate` |
| 二维码状态管理 | 冻结/注销/激活 | `/trace/qs/status` |
| 溯源查询 | 消费者扫码查询溯源信息 | `/trace/query/**` |

**二维码生成流程**：

```
1. 管理员创建产品批次
2. 管理员生成二维码 → 系统生成qsId(QS+时间戳+6位随机)
3. 构造签名原文: qsId|batchId|companyId|issueTime
4. SM2私钥签名 → signature
5. 构造扫码URL: https://xxx/scan?qsId=...&signPayload=...&signature=...
6. ZXing生成二维码图片
7. 区块链存证(QR_HASH): qsId + 签名 + 签名原文 → 上链
```

### 3.2 扫码行为监测模块 (qs-scan-service)

**核心功能**：

| 功能 | 说明 | API |
|------|------|-----|
| 扫码上报 | 消费者扫码记录 | `POST /scan/report` |
| 扫码日志查询 | 按二维码查扫码记录 | `GET /scan/logs/{qsId}` |
| 消费者反馈 | 投诉/举报提交 | `POST /scan/feedback` |
| 反馈处理 | 企业/管理员处置反馈 | `/scan/feedback/**` |

**扫码上报流程**：

```
1. 消费者扫码 → 前端调用 /scan/report
2. SM2公钥验签 → 验证二维码真实性
3. 检查二维码状态(active)和扫码次数
4. 计算跨区域距离(扫码位置 vs 企业位置, Haversine公式)
5. 更新设备画像(DeviceProfile: 新设备/风险设备判定)
6. 持久化扫码日志
7. 提取特征 → 调用 alert-service 风险评估
```

### 3.3 AI风险评估模块 (qs-alert-service)

**核心功能**：

| 功能 | 说明 | API |
|------|------|-----|
| 风险评估 | 规则引擎+AI融合决策 | `POST /alert/evaluate` |
| 预警列表 | 查询预警记录 | `GET /alert/list` |
| 规则管理 | Drools规则CRUD+热加载 | `/alert/rules/**` |
| 预警处置 | 确认/处置预警 | `/alert/disposal/**` |

**风险评估四阶段流程**：

```
阶段1: 特征提取
  scanCount1h, deviceCount1d, ipCount1h, timeVariance, locationVariance
  newDevice, riskDevice, distanceKm, deviceScanCount, maxAllowedScans

阶段2: 规则引擎评估 (Drools)
  动态DRL规则匹配 → ruleScore
  规则增强: 位置方差+跨区域距离+新设备+风险设备+高频扫码 → enrichedRuleScore

阶段3: AI模型推理 (ONNX)
  StandardScaler标准化 → 学生模型(3层MLP)推理 → softmax → aiScore

阶段4: 融合决策
  finalScore = aiScore × 0.6 + enrichedRuleScore × 0.4
  CRITICAL[86-100] → 自动冻结 + 邮件通知 + 区块链存证
  HIGH[61-85]      → 邮件通知 + 区块链存证
  MEDIUM[31-60]    → 系统通知
  LOW[0-30]        → 自动关闭
```

**知识蒸馏模型架构**：

```
教师模型(离线训练, ~15K参数):
  通道1: Transformer(2层4头, d=32) → 序列特征交互
  通道2: MLP(5→32→32) → 结构特征编码
  融合头: Linear(64→32→2) → 二分类logits

学生模型(在线部署, ~1.2K参数):
  Linear(5→32)→ReLU→BN→Dropout(0.3)
  Linear(32→16)→ReLU→BN→Dropout(0.2)
  Linear(16→2) → 二分类logits

蒸馏训练:
  温度 T=2
  loss = 0.6 × CrossEntropy + 0.4 × KL_Divergence × T²
```

**5维输入特征**：

| 特征 | 含义 | StandardScaler均值 | 标准差 |
|------|------|-------------------|--------|
| scan_count | 扫码次数 | 7.42 | 26.32 |
| time_variance | 时间方差 | 1.22 | 3.18 |
| location_variance | 位置方差 | 0.82 | 2.69 |
| device_count | 设备数量 | 5.60 | 29.28 |
| ip_count | IP数量 | 4.36 | 23.57 |

### 3.4 区块链存证模块 (qs-block-service)

**核心功能**：

| 功能 | 说明 | API |
|------|------|-----|
| 二维码签发存证 | QR_HASH | `POST /block/proof/qr` |
| 二维码冻结存证 | QR_FREEZE | `POST /block/proof/freeze` |
| 预警/反馈存证 | ALERT_EVENT | `POST /block/proof/event` |
| 存证验证 | 链上验证 | `GET /block/proof/verify` |
| 存证列表 | 查询历史 | `GET /block/proof/list/{key}` |
| 诊断 | 网关模式检查 | `GET /block/proof/diagnose` |

**Outbox异步上链流程**：

```
1. ProofService.save() → 写入blockchain_proof表(PENDING) + proof_outbox表(PENDING)
2. 事务提交后 afterCommit → 异步触发 processOutboxByProofId()
3. FiscoContractGateway.writeProof() → WeBASE /trans/handle → 合约save()
4. 成功 → 更新chain_status=SUCCESS, 记录txHash/blockNumber
5. 失败 → RETRY(退避10s×重试次数), 超过3次 → DEAD(写入死信表)
6. 定时调度(每3秒) → ProofOutboxDispatcher 补偿遗漏的outbox记录
```

**智能合约 ProofContract.sol**：

```solidity
// 联合键: keccak256(businessKey + proofType) — 同一qsId可存在QR_HASH和QR_FREEZE两种存证
function save(string businessKey, string proofType, string hash, string payload)
function verify(string businessKey, string proofType, string hash) returns (bool)
function getProof(string businessKey, string proofType) returns (...)
function hasProof(string businessKey, string proofType) returns (bool)
```


## 八、常见问题

### Q1: 服务启动报 Nacos 连接失败

确保 Nacos 已启动且端口 8848 可访问。检查各服务 `application.yml` 中 `spring.cloud.nacos.server-addr` 配置。

### Q2: 区块链存证返回 500

1. 检查 `gateway-mode` 是否为 `webase-sdk`
2. 检查 WeBASE-Front 是否可达: `curl http://192.168.230.131:5002/WeBASE-Front`
3. 检查合约地址是否正确（链上是否已部署新版合约）
4. 查看服务日志中的 `WeBASE write原始响应` 和 `WeBASE verify原始响应`

### Q3: 前端页面空白或报 Failed to fetch

1. 清除 Vite 缓存: `rm -rf frontend-vue/node_modules/.vite`
2. 重启前端: `npm run dev`
3. 检查 `http.js` 中 `BASE_URL` 是否指向正确的网关地址
4. 浏览器强制刷新: `Ctrl + Shift + R`

### Q4: AI 模型推理失败走 fallback

1. 检查 `qs_risk_model.onnx` 是否存在于 `qs-alert-service/src/main/resources/model/`
2. 检查 `qs_risk_scaler.json` 是否存在
3. 查看日志中 ONNX 加载错误信息
4. fallback 模式下系统仍可正常运行，只是评分使用线性公式

### Q5: 统计页面没有数据

统计页面依赖扫码日志数据。需要先通过消费者端扫码产生数据，统计页面才能显示。区域分布依赖 `device_profile` 表中的 city/province 字段。

### Q6: 如何切换 Mock/真实区块链模式

编辑 `qs-block-service/src/main/resources/application.yml`：

```yaml
app:
  blockchain:
    gateway-mode: mock        # Mock模式（本地测试）
    # gateway-mode: webase-sdk  # 真实链模式
```

重启 qs-block-service 即可。可通过 `/block/proof/diagnose` 接口确认当前模式。
